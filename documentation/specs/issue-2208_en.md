## 2. Context and Objectives

The assistant already has listing, status, diagnostic, and Recorder history tools, but no direct collector query or inventory of plugins configured for a thermostat with their own state. The objective is to reduce diagnostic time and maintainer workload. P0 reflects that operational value, not a demonstrated critical failure.

Scope: two new read-only LLM tools intended for publication by Home Assistant's official MCP server through Assist, subject to compatibility check V-01, each targeting one loaded, exposed VTherm. The first returns logs selected by VTherm and dates according to the existing collector. The second returns plugins actually configured for this VTherm and their available state, with declared coverage. This is neither a list of all installed plugins nor the global factory catalogue.

**Established facts:** the collector includes messages without a thermostat hint; factory registries are global; several linking mechanisms exist; the protocols read define no universal diagnostic-state contract. Neither requested tool is registered in the local existing tool list (S-02).

**Gap to address:** useful data resides in heterogeneous sources, sometimes only in diagnostic entities or targeted configuration. Returning only VTherm attributes does not cover the entire request. The proposals below assume neither a feasible uniform access mechanism nor universal coverage.

**Convergence 3:** comparison of the updated report, both v1.2 specifications, and both v1.2 designs. Same functional scope, now clarified by the received answers, without API/plugin expansion. R-01/R-02 are corrected in the designs; DIV-01/Q-04 and DIV-03/Q-02 are no longer blocking decisions. DIV-04 retains proposed selection and future measurements, not an unanswered ceiling question. Design predates these decisions; its conditional conclusions are reassessed in section 10 without editing its documents or confusing documentary convergence, final approval, and V-01/V-02 evidence.

## 3. Actors and Use Cases

| Actor                              | Role                                                                                                      |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------- |
| User / maintainer                  | Requests a diagnosis; selects the thermostat and optionally the period; approves remaining decisions.     |
| AI agent                           | Selects and calls tools; interprets data and its limitations; remains responsible for interpretation.     |
| Assist / Home Assistant MCP server | Publishes tools according to existing exposure; retains its general access mechanisms.                    |
| Log collector                      | Provides currently retained entries and applies its existing selection.                                   |
| Emitting integrations / plugins    | Ensure attribution of their logs; provide configuration links and states according to their capabilities. |

**UC-01, logs:** a request about an exposed VTherm triggers a query with dates or the default window. The tool returns available selected entries, effective criteria, and limit-exceeded/truncation information. The agent draws conclusions; the tool does not choose a cause.

**UC-02, plugins:** an inventory request for this VTherm triggers discovery in covered categories. The result distinguishes configured links, loading, availability, and plugin-specific state. Global configuration counts only if its application to this thermostat is demonstrated.

**UC-03, degraded data:** after startup, reload, or unavailability, a query returns facts still accessible and identified limitations. It does not reload, create, repair, or activate anything.

### P-01: Initial Coverage Approved under Q-01

The following four families and their seven examples are approved by the maintainer. Scope covers their identifiable configured links, not every third-party plugin that might use them. Upcoming plugins are not automatically covered; without a universal inverse contract, discovering their links or naming invisible categories on an installation cannot be guaranteed. Linking evidence below is inherited from earlier analyses, not rechecked this cycle.

| Category                                          | Verified examples and linking evidence                                                                                                                                                   | Retained coverage and limitation                                                                                                                                                                                                                                      |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CAT-01, external proportional algorithms          | SmartPI, Hysteresis, Pellet Regulation; thermostat `proportional_function` selection, then factory/handler; global or targeted options depending on the plugin (S-04, S-07, S-08, S-09). | Include the selected external algorithm even without an available factory or handler. Searching only for plugin climate entities would miss this example. `PluginClimate` provides no universal reverse registry of integrations using it.             |

**Evidence clarification, not a new decision:** for Heating Failure Detection, v1.2 design distinguishes persisted entries, entries available to the runtime model, configuration actually applied to the manager, and publication. The runtime dictionary may update before a reload finishes: its presence proves neither a loaded handler nor current application. It documents `options or data`, not a universal merge. An unloaded or disabled entry proves a declared link under P-01, not current application. A merged configuration view with unidentifiable central origin shall retain that limited provenance. The `heating_failure_detection_manager` publication can originate from the native or external manager: neither the key alone nor a persisted plugin entry proves its producer (S-18, S-19). Application and producer remain unknown without evidence; Q-02 accepts these gaps when further information is unavailable without authorizing assumed attribution. Q-01 approves families/examples, not a new technical discovery guarantee.

A plugin using several mechanisms shall not become several fictitious plugins: present one identity with verified links/roles. Actually distinct entries shall remain distinguishable. Global inheritance shall be attributed to the relevant target under plugin-specific rules, not solely because a global entry exists.

### P-02: Proposed 5,000 Ceiling and Selection Awaiting Approval

Current contract for final presentation: fixed ceiling **L = 5,000 entries per call**, proposed by the maintainer, with no pagination parameter. **Proposed default selection, not separately confirmed:** if collector selection contains N entries, retain its last L entries in the same collector order. This rule will be approved at the final presentation; it is not attributed to a separate explicit user answer. This is buffer insertion order, usually chronological, not a guarantee of timestamp sorting. Do not prioritize errors or reorder entries with identical timestamps.

For N less than or equal to L: return everything, zero omissions, limit exceeded and truncation false. For N greater than L: return L entries, declare N, N minus L omissions, limit exceeded and truncation true. These counts concern only the selected snapshot in the current buffer, never all emissions during the period. The requested period remains unchanged. First/last entries may not carry the minimum/maximum timestamps; these concepts shall remain distinct.

5,000 is the retained proposed ceiling, **not measured sufficiency**. Future tests shall select and document a representative one-hour routine-diagnostic example including unhinted messages, then verify delivery under this ceiling. No sample supplied or to be supplied by the user is required now; no name, installation, rate, or test channel is invented. Testing will record provenance, installation/verbosity, selected count/rate, omissions, observed volume, and delivery on the tested channel. If it exceeds the ceiling or the response is not delivered fully, record the gap and submit feasibility or ceiling for reassessment without claiming the one-hour objective is met. No sample or result is available in this cycle. An entry ceiling guarantees neither one hour of logs nor byte volume or transport capacity. High verbosity remains an explicit truncation case, not a reason to cap duration or change retention; no byte limit, pagination, or transport modification is implicitly authorized.

## 6. Functional Constraints

- **Authorization:** specification documents only. Explicit final approval of specifications, proposed selection, and updated design required before any separate development authorization; received answers do not provide that authorization.
- **Availability and operational safety:** no equipment command or regulation change shall result from a query, including on error. No restart, reload, or log-level change required by the tool.
- **Access:** preserve existing Assist exposure with no new tool-specific permissions or authentication; do not copy the Recorder tool's additional constraints.
- **Privacy:** the maintainer considers these logs non-sensitive and accepts mixed messages. This is a scope assumption, not an exhaustive audit. No masking or special treatment of ambiguous logs required; arbitrary private plugin configuration export remains out of scope.
- **History:** in-memory buffer defaults to 100,000 entries and a configured four-hour age, with periodic purge and possible eviction/restart losses (S-05). This guarantees neither four complete hours nor a query-period cap; no change requested.
- **Compatibility:** local VTherm 10.6.3 manifest and declared `vtherm_api>=0.7.0` dependency (S-16). Design documents local API 0.8.0, HACS minimum HA 2026.3.1, declared dev environment HA 2026.8.2, and October 2026 LLM comment; these certify neither the API 0.7.0 floor nor an HA/LLM/plugins/MCP matrix. V-01 shall verify publication, parameter validation, delivery, and userless-context capabilities. No version increase, dependency change, or HA rig authorized by this document.
- **Volume:** log-count limitation only within the approved scope; no pagination or period-duration cap. Maximum byte size and guaranteed response times unknown; no invented numeric requirement. The report does not decide a general prohibition on application response timeouts: the design's proposed absence of a deadline remains a candidate choice, not a confirmed user invariant. This review authorizes no new timeout or byte ceiling; any change to agreed constraints shall be submitted separately.
- **Regulation:** no specific regulatory constraint established by consulted sources.

## 8. Out-of-Scope Functions

- Heating/plugin commands, installation, activation, learning, repair, or configuration modification: incompatible with requested read-only behavior.
- Additional tool-specific authentication/roles/permissions: expressly rejected by the maintainer; general channel mechanisms remain unchanged.
- Corrected attribution, special removal of ambiguous messages, masking, or exhaustive audit of integration logs: emitter responsibility and accepted risk.
- AI interpretation, causal conclusions, or special protection against an agent interpreting data as instructions: agent responsibility, not these Tools.
- Pagination, query-duration cap, new retention/persistence, or reconstruction of lost logs: expressly out of scope.
- Global catalogue of installed plugins/factories, native managers presented as external plugins, universal third-party or inhibition-emitter inventory: do not answer the requested configured link or cannot be proved with the contracts read.
- Plugin internal-state history, charts/CSV, new file export, or a new MCP server: separate requests; existing Recorder/manual-export tools not replaced.
- #2191 correction or imposed changes to the API/every plugin: not authorized here; an additional contract is an option to submit to design.

## 9. Proposed Future Enhancements

- Voluntary per-plugin diagnostic/link contract only if a later need requires more than accepted partial states; define coverage, compatibility, adoption, and authorization before making it a requirement. No generic contract or plugin modification is currently required.
- Extend covered integrations and per-category states using verified examples; do not announce automatic third-party support.
- Reassess the log ceiling from observed rates within the accepted count-only boundary, without pagination or retention changes.

These possibilities are not current requirements and do not authorize any work.
