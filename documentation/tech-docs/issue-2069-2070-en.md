## Analysis and recommendation

### Relevance

The reported problem is real. With an effective command at the floor, the current predicates compare only with the `number` entity minimum; the valve is therefore reported as active although there is no heating demand. Changing the startup closing command to `_get_controlled_percent(0)` is consistent with `turn_off`.

### Conclusion

**Recommendation: request changes before merging.**

The new comparison introduces a functional regression for valid configurations: it compares an effective physical opening with `opening_threshold_degree`, which is a raw TPI demand threshold. This can report a valve receiving maximum demand as inactive.

## Review findings

### Blocking - raw threshold compared with a physical opening

The added `_active_threshold` property includes `self._opening_threshold`; `should_device_be_active` then compares this threshold with `self._percent_open`, while `is_device_active` compares it with `current_valve_opening`. However, `_percent_open` and the valve state are effective commands after conversion by `OpeningClosingDegreeCalculation`.

Counterexample accepted by the configuration flow:

- `opening_threshold_degree = 60`;
- `max_opening_degrees = "50"`;
- `min_opening_degrees = ""`;
- `max_closing_degree = 100`;
- raw TPI demand = 100%.

The algorithm sends 50% to the valve, its configured maximum. The PR then uses an active threshold of 60 and returns `False` for both predicates. VTherm can consequently publish `idle`, omit the valve from its active-device list, and fail to trigger consumers of that state, including the central boiler, despite 100% demand.

Expected correction: determine activity in one scale. The TPI demand threshold must be evaluated against raw demand, or the physical threshold compared with the effective opening must be calculated using the same conversion and per-valve limits. Add a regression test with `opening_threshold_degree > max_opening_degrees`, raw demand at 100%, and expected `heating` / active underlying device states.

### Minor - documentation is published in one language only

The PR adds the new behavior only to `documentation/en/over-valve.md`. The French, Czech, German, and Polish versions do not contain this information, although the repository publishes those guides and specification #1348 requires consistent terminology across languages.

Expected correction: add the paragraph to the four localized documents, or remove the documentation change from the PR and create an explicitly tracked translation task.

## Proposed scope

### Include on the #2070 resolution branch before merging

- Preserve the `max_closing_degree` floor correction in active states and in `check_initial_state`.
- Correct the comparison between the TPI threshold and the physical opening.
- Cover the above boundary case with an integration or focused test.
- Correct `OpeningClosingDegreeCalculation` so the effective command never drops below `100 - max_closing_degree`, including when demand reaches or exceeds `opening_threshold_degree`.
- Add a test matrix covering threshold crossing, default values, configured minima above and below the floor, and both consumers of the algorithm: `over_valve` and `over_climate` valve regulation.
- Keep the multilingual documentation aligned if behavior documentation remains in this PR.

### Out of scope

- Changes to `UnderlyingValveRegulation`, which already overrides its activity predicates.
- Configuration changes not required to guarantee the floor or activity detection; additional validation will be considered only if the algorithmic correction cannot preserve existing configurations.

## Impacts and risks

| Subject | Risk | Severity | Likelihood |
| --- | --- | --- | --- |
| Introduced regression | Real demand can be reported inactive when the physical maximum is below the TPI threshold. | High | Medium |
| Central boiler and diagnostics | Consumers of `is_device_active` may not activate. | High | Medium |
| Startup/reload | Returning to the floor is aligned with the intended behavior and limited to `over_valve`. | Low | Low |
| #2070 correction | The formula must become monotonic and maintain the floor without breaking existing configurations. | High | Medium |
| Documentation | Localized guides are inconsistent. | Low | High |

## Alternatives considered

1. Compare activity with raw TPI demand: directly respects the meaning of `opening_threshold_degree`; requires exposing that demand to the underlying entity.
2. Convert the TPI threshold into a physical threshold for each valve: keeps comparisons at underlying level; must apply the same formula and limits as command dispatch.
3. Forbid configurations where `max_opening_degrees < opening_threshold_degree`: reduces the risk, but changes existing validation and does not address the general scale mismatch.

Option 1 or 2 is preferable. Option 3 alone is not recommended.
